# 个人中心模块开发经验总结

## 1. 流程回顾

本次开发遵循了从需求分析到验证的完整流程：

```
分析选题要求 → 对比参考项目 → 确认技术方案 → 开分支 → 实施 → 验证 → 修复 → 完成
```

关键节点：

1. **选题要求分析**：个人中心 = 个人信息 + 关键词管理 + 关注领域管理 + 新闻源配置
2. **方案讨论**：确定用 ES + IK 分词器替换 jieba 来实现关键词匹配
3. **开功能分支**：`feature/user-center` 从 `feature/frontend` 分出
4. **逐层实现**：ES 基础设施 → 后端 API → 前端页面
5. **验证修复**：verification agent 发现 3 个问题（关键词去重、死代码、updatedAt），逐一修复

## 2. 重要教训

### 2.1 先检查所有分支再确认实现状态

第一轮评估时，我判断"传播溯源与路径分析未实现"，但实际它已经在一个独立分支
`feature/propagation-analysis` 里写好了，只是没合并到当前分支。

**教训**：评估项目完成度前，必须 `git branch -a` + `git log --all --oneline --graph` 看清楚每个分支有什么。

### 2.2 技术选型要让用户参与

关键词匹配方案从"pkuseg 还是 ES"这个问题引出，中间还讨论了匹配准确率百分比、部署成本等。让用户对投入产出比有概念后再决定，比直接替用户选要好得多。

### 2.3 功能分支不要删别的模块

`feature/propagation-analysis` 分支虽然实现得很好，但它把整个 web/ 前端和 fake-detection 模块都删了（因为这些不是传播分析需要的）。这导致它无法直接合并到 `feature/frontend`。

**教训**：每个功能分支应该保持项目完整可运行，只增加自己的代码，不删除别人的。

### 2.4 ES 的 try-catch 设计模式

ES 不可用不应该阻断主业务流程。`ContentServiceImpl.saveCleanResult()` 里的做法是正确的：

```java
try {
    searchSyncService.indexArticle(clean);
} catch (Exception e) {
    System.err.println("[ES] 同步失败: " + e.getMessage());
}
```

这种"尽力而为"的模式保证了即使 ES 挂了，文章清洗流水线仍然正常工作。

### 2.5 数据去重应该有多层防护

Verification agent 发现关键词和领域可以被重复添加。修复时做了两层保护：

- 服务层：`selectCount` 检查是否已存在
- 数据库层：`UNIQUE KEY (user_id, keyword)`

**教训**：CRUD 操作中，Create 必须有幂等性考虑。单独靠一层保护不够，服务层 + 数据库层两层最稳。

### 2.6 复用优于新建

新闻源订阅功能没有新建一张独立的"用户新闻源"表，而是建了关联表 `user_source_subscription` 引用 `crawl_news_source`。这样：

- 不需要维护两份新闻源数据
- 爬虫管理者增删新闻源，用户订阅自动同步
- 查询用户订阅时 JOIN 即可

**教训**：先看看现有表能不能复用，不要习惯性地新建表。

## 3. 代码模式总结

### 3.1 后端分层（已形成的模式）

```
system/
  controller/     → @RestController, @RequestMapping("/api/xxx")
  service/        → 接口定义
  service/impl/   → @Service 实现
  entity/         → @TableName, MyBatis-Plus Entity
  mapper/         → extends BaseMapper<Entity>
  dto/            → record (Java 17) + @Valid 校验注解
  vo/             → record + static from(Entity) 工厂方法
```

### 3.2 前端分层

```
web/src/
  api/            → Axios 请求封装，一个模块一个文件
  views/          → Vue SFC，一个页面一个目录
  router/         → 路由定义 + beforeEach 鉴权守卫
  layout/         → MainLayout（侧边栏 + 顶栏 + 内容区）
  stores/         → Pinia 状态（当前只有 user.js）
```

### 3.3 API 路径命名

- 统一 `/api/模块名/子资源` 格式
- GET 查询、POST 创建、PUT 修改、DELETE 删除
- 分页参数：`pageNum`, `pageSize`

### 3.4 异常处理

- 模块级异常继承 `RuntimeException`
- `GlobalExceptionHandler` 统一捕获并返回标准 JSON
- 外部服务调用失败返回 502

## 4. 可以改进的地方

- MyBatis XML mapper 目录全是 `.gitkeep`，目前全用注解，后续复杂查询可能需要 XML
- `updatedAt` 只在 `updateProfile()` 手动设了一次，其他地方的更新时间字段可能也有遗漏
- 前端没有全局 loading/error 拦截的封装，每个页面自己 try-catch 处理

## 5. 聚类模型升级与缺陷修复 (2026-07-14)

### 5.1 嵌入模型切换：BGE-small → M3E-large

**背景**：HDBSCAN聚类使用384维BGE-small模型，中文语义区分度有限。

**过程**：
1. BGE-small（384维，92MB，CPU推理快）→ M3E-large（1024维，~400MB，中文优化）
2. 模型下载到 `D:/huggingface_cache`（E盘无BUILTIN\Users写权限）
3. `embedding_service.py` 添加 `model_kwargs={"cache_dir": ...}` 解决transformers 5.x的`cache_folder`废弃警告
4. M3E的tokenizer比BGE严格，遇到数据库中的孤立代理字符（lone surrogates）直接抛出`TextEncodeInput`错误

**效果**：1024维向量对中文语义区分更好，聚类质量显著提升（如"人大硕士嫖娼学位造假"10篇文章精准聚合）。

### 5.2 孤立代理字符（Lone Surrogates）问题

**现象**：M3E-large的tokenizer报错 `TextEncodeInput must be Union[TextInputSequence, Tuple[InputSequence, InputSequence]]`

**根因**：数据库中部分文章标题包含不合法Unicode（如`\udca7`、`\udcab`），这些是UTF-8编码错误导致的孤立代理字符。BGE-small的tokenizer忽略它们，M3E的tokenizer严格拒绝。

**修复**：在 `EmbeddingService.encode()` 和 `ClusteringService._generate_by_llm()` 中添加 `_sanitize()` 方法：
```python
text.encode("utf-8", errors="surrogateescape").decode("utf-8", errors="replace")
```
用 `surrogateescape` 捕获非法字节，再用 `replace` 替换为 `�`，保证tokenizer不报错。

### 5.3 DeepSeek API Key 统一配置

**现象**：事件命名返回"未命名事件"，摘要/情感分析全部降级到本地规则。

**根因**：intelligence服务没有`.env`文件，`DEEPSEEK_API_KEY`环境变量为空。

**修复**：
1. 从`services/report/.env`复制API Key（`sk-aa2e6248788348feb7aad8faaa70c838`）
2. 创建`services/intelligence/.env`，添加`load_dotenv()`到`main.py`
3. 效果：事件标题由DeepSeek LLM生成，如"也门胡塞武装劫持红十字会飞机"

### 5.4 摘要截断修复

**根因**：`summary_service.py`中`max_tokens=800`限制包含7个字段的JSON，降级时`content[:500]`硬截断。

**修复**：
- `max_tokens`: 800 → 2000
- 降级截断改为在句号/问号/感叹号等自然句末结束，避免中间切断

### 5.5 趋势预测图表不渲染

**现象**：点击"趋势预测"按钮，对话框中只显示预测方法和趋势走向文字，没有图表。

**根因**：`event/index.vue`中时序bug：
```js
try {
  trendData.value = res.data
  await nextTick()
  renderTrendChart()  // ← 此时 trendLoading 仍为 true
} finally {
  trendLoading.value = false  // ← v-if="!trendLoading" 导致chart DOM不存在
}
```
`v-if="!trendLoading"` 控制着chart的DOM元素，`renderTrendChart()`调用时`trendLoading`还没设为false，DOM不存在，`trendChartRef.value`为null，函数提前return。

**修复**：将`trendLoading.value = false`移到`renderTrendChart()`之前。

### 5.6 关键教训

- **Python .pyc缓存**：修改代码后必须`rm -rf __pycache__`，否则可能跑的是旧代码
- **uvicorn --reload**：首次请求后可能触发重载，导致模型重新加载和状态丢失，测试时建议不加`--reload`
- **嵌入模型切换时参数需重新调优**：`cluster_selection_epsilon`在384维和1024维空间下效果不同，但M3E用默认值0.08也能正常工作
- **Windows端口僵尸**：`taskkill`后端口可能仍被占用，需确认进程完全退出后再重启
- **HuggingFace缓存放机械硬盘可行**：M3E-large ~400MB，冷启动约30秒加载，之后推理在内存中
